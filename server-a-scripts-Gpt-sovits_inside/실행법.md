# GPT-SoVITS 자동화 실행법 (Host/Conda + Docker)

이 문서는 `server-a-scripts-Gpt-sovits_inside` 자동화 구성요소를 실제로 실행하는 절차를 정리합니다.

## 1. 실행 모드 선택

- Host/Conda + `systemd` (기존 방식)
- Docker + Compose Sidecar (권장, 최상위 `docker-compose.yaml` 기준)

## 2. Docker + Compose Sidecar 방식 (권장)

### 대상 서비스

- `gpt-sovits-cu128` (GPT-SoVITS 본체)
- `gpt-sovits-files-api` (File Scanner API, `10001`)
- `gpt-sovits-training-api` (Training API, `10002`)
- `backend`
- `frontend`

### 사전 조건

- Docker / Docker Compose 사용 가능 환경
- GPU/NVIDIA 런타임 사용 환경 (특히 `gpt-sovits-cu128`, `gpt-sovits-training-api`)

### 빌드

```bash
docker compose -f docker-compose.yaml build gpt-sovits-files-api gpt-sovits-training-api
```

### 실행

```bash
docker compose -f docker-compose.yaml up -d
```

### 상태 확인

```bash
docker compose -f docker-compose.yaml ps
```

또는 자동화 스크립트 사용:

```bash
cd madcamp-Screening-Humanity-AI-Server/server-a-scripts-Gpt-sovits_inside
./compose_manager.sh status
```

### 로그 확인

```bash
docker compose -f docker-compose.yaml logs -f gpt-sovits-cu128 gpt-sovits-files-api gpt-sovits-training-api
```

또는:

```bash
cd madcamp-Screening-Humanity-AI-Server/server-a-scripts-Gpt-sovits_inside
./compose_manager.sh logs
```

### 재시작/중지

```bash
docker compose -f docker-compose.yaml restart gpt-sovits-cu128 gpt-sovits-files-api gpt-sovits-training-api
docker compose -f docker-compose.yaml stop gpt-sovits-cu128 gpt-sovits-files-api gpt-sovits-training-api
```

또는:

```bash
./compose_manager.sh restart
./compose_manager.sh stop
```

### 헬스 체크

```bash
curl http://localhost:10001/api/health
curl http://localhost:10002/api/health
```

확인 포인트:

- `resolved_root`가 `/workspace/GPT-SoVITS`로 잡히는지
- `root_structure_ok`가 `true`인지

### Dry Run 학습 테스트 (`training_api.py`)

```bash
cd madcamp-Screening-Humanity-AI-Server/server-a-scripts-Gpt-sovits_inside
TRAINING_API_URL=http://localhost:10002 python test_training.py
```

`dry_run=True`로 실행되므로 실제 학습 대신 파이프라인 흐름/상태/로그 경로를 검증할 수 있습니다.

## 3. Host/Conda + systemd 방식 (기존 방식 유지)

이 방식은 Docker가 아닌 Server A 호스트에서 `/opt/GPT-SoVITS` 기준으로 실행합니다.

### 파일 배치

아래 파일들을 `/opt/GPT-SoVITS`에 배치합니다.

- `training_api.py`
- `file_scanner_api.py`
- `gpt-sovits-files.service`
- `gpt-sovits-training.service`
- `service_manager.sh`

### 의존성 설치 예시

```bash
cd /opt/GPT-SoVITS
pip install fastapi uvicorn python-multipart aiofiles pydub PyYAML
# pydub 사용 시 ffmpeg 필요
# Ubuntu 예시: sudo apt-get install -y ffmpeg
```

### 서비스 설치 및 실행

```bash
cd /opt/GPT-SoVITS
chmod +x service_manager.sh
./service_manager.sh install
./service_manager.sh start
```

### 서비스 관리

```bash
./service_manager.sh status
./service_manager.sh logs
./service_manager.sh restart
./service_manager.sh stop
```

주의:

- `service_manager.sh`는 Host/systemd 전용입니다.
- Docker 컨테이너 내부에서 이 스크립트를 그대로 사용하는 구조가 아닙니다.

## 4. 최상위 Compose 파일 구분

- `docker-compose.yaml`
  - 현재 메인 파일
  - Docker 기반 GPT-SoVITS 본체 + 자동화 sidecar 포함
- `docker-compose.conda.yaml`
  - 기존(비-Docker GPT-SoVITS / conda 기반 운영 전제) compose 보존본

## 6. 리팩토링 작업 실행 규칙 (보수적 절차)

`server-a-scripts-Gpt-sovits_inside` 리팩토링은 아래 순서를 지켜서 진행합니다.

### 6.1 권장 순서

1. 행동 고정(회귀 기준 확보)
2. 주석/섹션 정리 (읽기 쉽게)
3. 명백한 버그/죽은 코드 제거
4. 공통 유틸 추출 (`runtime`, `process`, `http_utils`)
5. `training_core`, `file_core`로 로직 이동
6. 엔드포인트를 thin controller로 정리
7. 정적/런타임 회귀 검증
8. 문서 정합성 업데이트

### 6.2 작업 중 지켜야 하는 규칙

- 포트/엔드포인트/응답 키 변경 금지 (합의 없는 경우)
- 큰 구조 변경 전에 반드시 정적 검증 실행
- 리팩토링 커밋 단위를 작게 유지 (문제 생기면 되돌리기 쉽게)
- 함수 분해 시 로그 파일명/상태 문자열 유지
- 과분할 금지: `gsv_automation` helper 모듈 6개 내외 유지

### 6.3 실패 시 롤백 기준

아래 중 하나라도 깨지면 해당 단계 변경을 되돌리고 다시 쪼개서 진행합니다.

- `python3 -m py_compile` 실패
- 엔드포인트 목록(path/method) 변경
- `test_training.py` dry-run 흐름 깨짐
- `/api/health` 응답 필드 누락

## 8. URL/도메인 변경 시 작업 순서 (권장)

서비스 주소를 바꿀 때는 파일 여러 군데를 수정하지 말고 env/compose부터 바꿉니다.

1. FRONT 공개 API 주소
- `NEXT_PUBLIC_API_URL`
- (선택) `NEXT_PUBLIC_MEDIA_BASE_URL`, `NEXT_PUBLIC_BACKEND_DISPLAY_URL`

2. BACK → Server A / LLM / TTS 주소
- `SERVER_A_FILES_API_URL`
- `SERVER_A_TRAINING_API_URL`
- `TTS_BASE_URL`
- `OLLAMA_BASE_URL`

3. 테스트 스크립트 주소 (필요 시)
- `TRAINING_API_URL`
- `VLLM_URL`
- `OLLAMA_HOST`

규칙:

- 코드 내부 `localhost` 문자열을 직접 수정하기보다 env/compose override를 우선 사용
- Docker 모드에서는 `docker-compose.yaml`의 `${VAR:-default}` 값을 활용
