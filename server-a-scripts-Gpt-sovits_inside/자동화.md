# GPT-SoVITS Server A 자동화 구성 가이드 (Host + Docker Sidecar)

이 문서는 `madcamp-Screening-Humanity-AI-Server/server-a-scripts-Gpt-sovits_inside` 폴더의 실제 구성요소를 기준으로, GPT-SoVITS Server A 자동화 기능을 정확히 정리한 문서입니다.

핵심 목표는 다음 2가지입니다.

1. `file_scanner_api.py` (포트 `10001`)로 모델/오디오/학습용 파일 관리
2. `training_api.py` (포트 `10002`)로 학습 파이프라인 자동화

이 자동화 기능은 두 가지 운영 모드를 지원합니다.

- Host/Conda + `systemd` 모드 (`service_manager.sh` 사용)
- Docker + Compose Sidecar 모드 (`compose_manager.sh` 또는 `docker compose` 사용)

## 1. 기준 폴더 및 현재 상태

- 기준 폴더: `madcamp-Screening-Humanity-AI-Server/server-a-scripts-Gpt-sovits_inside`
- 이 폴더를 자동화 코드/문서의 단일 기준 소스로 사용합니다.
- IDE 탭에 보이는 `server-a-scripts-Gpt-sovits_폴더_내에_위치하게됨` 경로는 현재 디스크 기준 실체가 없을 수 있는 이전 경로/잔여 탭입니다.

## 2. 구성 요소 (실제 파일 기준)

### A. 운영 API

- `file_scanner_api.py`
  - 포트: `10001`
  - 역할: 모델 파일/학습용 음성 파일 조회 및 관리, 오디오 준비/검증
- `training_api.py`
  - 포트: `10002`
  - 역할: 오디오 전처리, ASR, 데이터 전처리, 학습 파이프라인 오케스트레이션

### B. Host(systemd) 운영 스크립트/서비스

- `service_manager.sh`
  - 역할: `systemd` 서비스 설치/시작/중지/재시작/상태/로그 관리
  - 주의: Docker 컨테이너 내부에서는 사용하지 않음
- `gpt-sovits-files.service`
  - `file_scanner_api.py`용 `systemd` 서비스 정의
- `gpt-sovits-training.service`
  - `training_api.py`용 `systemd` 서비스 정의

### C. 테스트/검증 스크립트

- `test_training.py`
  - `training_api.py`에 Dry Run 학습 요청 및 상태/로그 조회 테스트
  - 환경변수 지원:
    - `TRAINING_API_URL` (기본 `http://localhost:10002`)
    - `TRAINING_TEST_MODEL_NAME`
    - `TRAINING_TEST_UPLOAD_PATH`
    - `TRAINING_TEST_VERSION`
- `temp_runner.py`
  - 비동기 subprocess 로그 스트리밍 유틸/테스트용 러너
- `test_streaming.py`
  - 스트리밍 로그 테스트용 목업 프로세스
- `verify_streaming.py`
  - `temp_runner.py` 기반 로그 스트리밍 검증 스크립트

### D. Docker 운영 자산 (Sidecar 모드)

- `docker/Dockerfile.automation`
  - 자동화 API sidecar 전용 파생 이미지 정의
- `docker/requirements-automation.txt`
  - 자동화 API 추가 의존성 목록
- `docker/run-file-scanner.sh`
  - `file_scanner_api.py` 실행 엔트리포인트
- `docker/run-training-api.sh`
  - `training_api.py` 실행 엔트리포인트
- `compose_manager.sh`
  - Docker Compose 기반 운영 스크립트 (`start|stop|restart|status|logs`)

## 5. 경로 정책 (Host/Docker 겸용)

- `systemd` 서비스(`gpt-sovits-files.service`, `gpt-sovits-training.service`)도 이 경로를 기준으로 동작

  1. `/workspace/GPT-SoVITS`
  2. `/opt/GPT-SoVITS`
- `/api/health` 응답에 `resolved_root`, `root_source`, `root_structure_ok` 포함 (문서/운영 확인용)

## 8. 운영 모드별 관리 방식

### A. Host/Conda + systemd 모드

- 사용 스크립트: `service_manager.sh`
- 명령:
  - `./service_manager.sh install`
  - `./service_manager.sh start`
  - `./service_manager.sh stop`
  - `./service_manager.sh restart`
  - `./service_manager.sh status`
  - `./service_manager.sh logs`

### B. Docker + Compose Sidecar 모드

- 최상위 compose 파일: `docker-compose.yaml`
- 레거시(비-Docker GPT-SoVITS 전제) compose 보존본: `docker-compose.conda.yaml`
- 사용 스크립트: `compose_manager.sh`
- 명령:
  - `./compose_manager.sh start`
  - `./compose_manager.sh stop`
  - `./compose_manager.sh restart`
  - `./compose_manager.sh status`
  - `./compose_manager.sh logs`

## 9. Docker Sidecar 아키텍처 요약

### 구성

- `gpt-sovits-cu128` (본체, 기본 GPT-SoVITS 포트 `9871/9872/9873/9874/9880`)
- `gpt-sovits-files-api` (sidecar, `10001`)
- `gpt-sovits-training-api` (sidecar, `10002`)

### 설계 이유

- 기존 `service_manager.sh`는 `systemd` 전용으로 Docker 컨테이너 내부에 직접 적용하기 어려움
- 자동화 API를 sidecar로 분리하면 GPT-SoVITS 본체 설정을 유지하면서도 자동화 기능을 Docker에서 안정적으로 추가 가능
- 본체/sidecar가 `sample_train_voice`, `logs`, `TEMP`, `GPT_weights*`, `SoVITS_weights*` 볼륨을 공유하여 기능 일관성 확보

## 10. 백엔드 연동 포인트 (Docker 로컬 개발 기준)

최상위 `docker-compose.yaml`에서 `backend` 서비스 환경변수로 다음 값을 오버라이드합니다.

- `SERVER_A_FILES_API_URL=http://gpt-sovits-files-api:10001`
- `SERVER_A_TRAINING_API_URL=http://gpt-sovits-training-api:10002`
- `TTS_BASE_URL=http://gpt-sovits-cu128:9880`
- `SERVER_A_TRAIN_VOICE_ROOT=/workspace/GPT-SoVITS/sample_train_voice`
- `SERVER_A_LOGS_ROOT=/workspace/GPT-SoVITS/logs`
- `SERVER_A_TEMP_ROOT=/workspace/GPT-SoVITS/TEMP`

## 11. 주의사항

- 최상위 저장소 루트를 `- .:/workspace/GPT-SoVITS`로 마운트하면 이미지 내부 GPT-SoVITS 코드가 가려질 수 있으므로 사용하지 않습니다.
- Docker 모드에서는 자동화 API를 sidecar 이미지로 빌드해야 합니다 (`docker/Dockerfile.automation`).
- 현재 문서/코드는 Host와 Docker 둘 다를 지원하지만, 실제 Docker 런타임 검증은 Docker 가능한 환경에서 수행해야 합니다.

## 12. 코드 아키텍처 유지보수 규칙

이 섹션은 `server-a-scripts-Gpt-sovits_inside`를 장기적으로 유지보수할 때 지켜야 하는 규칙입니다.

### 12.1 외부 계약(절대 함부로 바꾸지 않는 것)

- 엔드포인트 파일명 유지:
  - `training_api.py`
  - `file_scanner_api.py`
- 포트 유지:
  - `10001` (File Scanner API)
  - `10002` (Training API)
- 엔드포인트 path/method 유지
- backend가 참조하는 응답 키 이름 유지 (1차 리팩토링에서 정리 금지)
- 로그 파일명/상태 문자열 유지 (`pipeline.log`, `status.json`, `queued`, `processing`, ...)

### 12.2 내부 모듈 구조 규칙 (과분할 금지)

리팩토링용 내부 모듈은 `gsv_automation/`에 두되, 파일 수를 과하게 늘리지 않습니다.

- 목표 구조 (6개 내외):
  - `gsv_automation/runtime.py`
  - `gsv_automation/process.py`
  - `gsv_automation/http_utils.py`
  - `gsv_automation/training_core.py`
  - `gsv_automation/file_core.py`
  - `gsv_automation/__init__.py`

핵심 원칙:

- 엔트리포인트는 thin controller
- 실제 로직은 core/service 함수로 이동
- 너무 잘게 쪼개지 말고 연관성 높은 기능끼리 묶어서 관리

### 12.3 적용하는 리팩토링 기법 (명시적)

- `Characterization Refactoring`: 먼저 현재 동작/응답/엔드포인트를 고정하고 시작
- `Extract Function`: 긴 함수(특히 `training_pipeline`) 단계 분해
- `Introduce Parameter Object`: 경로/컨텍스트/dataclass로 묶기
- `Thin Controller + Service Layer`: FastAPI route는 transport만 담당
- `Consolidate Duplicate Code`: subprocess/에러응답/오디오 처리 중복 제거
- `Guard Clauses / Fail Fast`: 중첩 분기 줄이기
- `Separate Query from Modifier`: 조회와 수정 책임 분리

### 12.4 금지사항 (보수적 리팩토링 기준)

- 포트/엔드포인트 변경
- backend와 합의 없는 응답 키 변경
- 로그 파일명/상태 문자열 변경
- 테스트 없이 대규모 구조 변경
- 주석 없이 복잡도 높은 함수 추가

## 13. 주석 작성 규칙 (공부한 흔적 남기는 스타일)

이 프로젝트의 핵심 파일은 나중에 다시 봤을 때 “내가 왜 이렇게 짰는지”가 바로 보여야 합니다.

### 13.1 톤/스타일

- 한국어 중심 (라이브러리/식별자/CLI는 영어 유지)
- 설명은 짧지만 이유는 반드시 포함
- 실무 경고형 주석 허용 (예: 여기 건드리면 backend 깨짐)
- 코드 그대로 읽는 주석 금지

### 13.2 함수 앞 주석 템플릿 (권장)

복잡한 함수(학습 단계/파일 조작/오디오 처리)는 아래 항목을 기준으로 적습니다.

- 역할 (이 함수가 실제로 하는 일)
- 왜 여기서 처리하는지 (레이어 책임 이유)
- 입력/출력 의미 (타입 이름 말고 실제 의미)
- 부작용 (파일 생성/삭제, subprocess, 로그 기록, 상태 변경)
- 실패/예외 처리 정책
- 주의 (호환성 계약, 운영 중 실수 포인트)

### 13.3 inline 주석 규칙

- 꼭 필요한 줄에만 적기
- 외부 툴 positional 인자 순서
- dry_run 보정 이유
- 응답 키/호환성 유지 이유
- 보안 검증 포인트 (경로 포함 관계 등)

예시 톤:

- `여기 응답 키는 backend에서 그대로 읽어서 씀. 1차 리팩토링에서는 이름 바꾸지 않음.`
- `dry_run에서도 뒤 단계 회귀 체크하려고 dummy 파일을 일부러 만든다.`

### 13.4 TODO / FIXME / HACK 규칙

- `TODO`: 다음 작업 + 어디서/언제 정리할지
- `FIXME`: 현재 위험/버그 + 재현 조건
- `HACK`: 임시 우회 + 왜 필요한지 + 제거 조건
